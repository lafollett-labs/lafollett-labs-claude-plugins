## [Unreleased]

### Fixed
- **issue-manager `create` duplicated or wiped an epic's Story Breakdown (`issue-manager` v1.0.7, marketplace 1.29.9).** The section regex ended on `\Z`, which JavaScript reads as a literal `Z`, not end-of-input. When the breakdown was the epic's last section, it never matched and a second, flat breakdown was appended. When it did match, the list was regenerated from `.github-state.json` as all `- [ ]`, dropping checked items, phase subheadings and hand-written titles. Either result was then pushed to the GitHub epic. The anchor is now `(?![\s\S])`. Existing lines are kept as written, only children not yet referenced are appended, `init`/template placeholders are replaced, and GitHub is not edited when nothing changed. 8 `node:test` cases, 5 of which fail on the old algorithm; CI runs them.

### Changed
- **round-5 remediation: two shapes the guard chain still mishandled (`plugin-janitor` v0.1.9, marketplace 1.29.8).** A non-string `installPath` — an object, a list, a number, a boolean — passed the `if not raw` emptiness check, because all of them are truthy, and reached `Path(raw)`, which raised a bare `TypeError` traceback rather than the schema-drift exit every other unrecognised shape produces. Nothing was ever deleted, so this was only a broken contract, but a registry whose `installPath` became an object is precisely the drift that message exists for. It now exits like the rest.
  - The relative-path guard added an hour earlier was itself too broad: `~/...` is not absolute either, so one such entry hard-exited before any report and disabled the tool outright, where the previous version had reported it dangling and carried on. `~` names the home directory unambiguously, so it is expanded and then treated like any other absolute path. What remains relative after expansion still aborts.
  - 47 -> 49 tests.
- **a relative `installPath` deleted a live install, silently (`plugin-janitor` v0.1.8, marketplace 1.29.7).** Found by continuing to attack the round-4 fix rather than by any reviewer: a relative path resolves against the process working directory, so whether an install looked reachable depended on where janitor happened to be run from. Alone it was harmless — the reachability guard refused the run. Beside a single absolute entry it was not: something *was* reachable so the guard stayed quiet, the relative entry's live install was classed stale and deleted, and the self-check stayed silent too, because that path had already been counted as dangling and was therefore excluded from the "did I just delete something live" comparison. Exit 0, no warning. Every earlier probe of this shape had used a single-entry registry, where the guard masked it — the blind spot was in the test matrix, not only in the code. An `installPath` is absolute; a relative one is a shape this tool does not recognise, and now aborts like every other unrecognised shape. 46 -> 47 tests.
- **round-4 remediation: the identity fix could delete what it could not identify (`plugin-janitor` v0.1.7, marketplace 1.29.6).** `ident()` returns `None` when `stat` fails, and `None` was filtered out of `installed_ids` — but the filter protects the set and the *predicate* is what decides. `ident(v.path) not in installed_ids` is true for `None`, so a version that could not be stat'ed between the directory walk and the staleness test fell straight through to stale and `--yes` deleted it, with `THIS IS A BUG — janitor removed a live install` printed afterwards. Reproduced by failing `stat` for exactly one live install's path, with a second reachable install present so the unreachable-registry guard could not mask it. Reachable in practice through a transient failure — `ESTALE` on a network home, an autofs timeout, a concurrent `marketplace update` — since `is_dir()` and `os.stat` are the same syscall, so this is a race rather than a steady state. Not knowing what a directory is cannot be grounds for removing it: the test is now `(i := ident(v.path)) is not None and i not in installed_ids`.
  - The identity change had also quietly narrowed two path forms, both found by re-running the full matrix rather than by reading. `os.stat` cannot walk through a missing intermediate component, so an `installPath` of `<cache>/mk/nothere/../keep/1.0.0` — which the string comparison normalised lexically — failed to stat, was classed dangling, and the reachability guard then refused the entire run over one entry. `ident()` now resolves before stat'ing, and the dangling classification tests the resolved path rather than the raw one, which is what every other comparison in the file already used.
  - 44 -> 46 tests. The guard matrix is now eleven path forms — absolute, differing case, trailing separator, `..`, `/.`, live-beside-dangling, all-dangling, relative, tilde, empty string, no entries — each asserting four things at once: whether the run was refused, that the live install survived, that a genuinely stale version still went, and that the self-check never fired.
- **round-3 remediation: janitor decided staleness by spelling, and deleted a live install because of it (`plugin-janitor` v0.1.6, marketplace 1.29.5).** Reported as awareness-only because it predates this work and reproduces identically two commits back — fixed anyway, because the failure is a deleted install on the filesystem this most often runs on. macOS is case-insensitive by default, so a registry recording `.../cache/MKT/plug/1.0.0` for a directory on disk at `.../cache/mkt/plug/1.0.0` passes `is_dir()` — the install is reachable and the new guard is correctly silent — and then fails `str(...resolve())` equality, so the version is classed stale and removed. The self-check catches it and says `THIS IS A BUG`, which is true, and says it after the deletion. Staleness is now decided by `(st_dev, st_ino)`, which settles case, symlinks, trailing separators and `..` in one move rather than four. 41 -> 44 tests; the guard matrix was re-run across all nine path forms to confirm identity did not make everything look installed.
  - The round-1 entry above named `--allow-empty-registry` as the escape hatch and the round-2 entry announced renaming it. Nothing here has been released, so this whole block is one release note and a reader would have met two names for one flag; it now names only the one that exists.
  - One more justification paragraph cut from janitor's SKILL.md — the table row directly above it already stated the same behaviour verbatim.
- **round-2 review remediation — 1 HIGH, 3 MEDIUM, 3 LOW (`watchwith` v1.0.3, `plugin-janitor` v0.1.5, marketplace 1.29.4).** Round 2 existed to confirm the round-1 fixes; it found that one of them was incomplete and that two of them introduced new defects. Both reviewers reproduced the HIGH again, independently, on a fix that had already been shipped.

A registry that names sixteen, all of whose paths point at a home directory that has since been renamed, parses fine, passes the shape validation, and is equally useless as a reachability oracle — every version on disk looks unreachable and `--yes` took the whole cache, `exit 0`, `verified: 0/3 installs intact`. The same hole swallowed a relative `installPath` and an unexpanded `~`. The test is now whether *any* install resolves to a directory that exists: `reachable = live - dangling`. This is a moved cache, a restored backup, or a changed path scheme — not a hypothetical.

The span is asked again after that answer comes back — which is what the round-1 text did before it was folded into one call.

- `plugin-janitor` (v0.1.2, marketplace 1.29.1): **it swept the versions and left the shelf.** Removing a plugin's last version leaves the `<plugin>` directory those versions lived in, empty — and `versions()` only names things exactly three levels under `cache/`, so no later run would ever mention it again. Found by running it: the screenscribe to watchwith rename removed two versions and left `cache/lafollett-labs-claude-plugins/screenscribe/` behind as a hollow shell, which is the same stale cache entry the tool exists to remove, in the one shape it could not see. `<marketplace>` directories have it too, when their last plugin goes.
  - The sweep is `rmdir`, never `rmtree`, and that is the safety property rather than a stylistic preference: a directory still holding anything — a stray file, a symlink, a version whose removal was refused — cannot be taken, so an error in the arithmetic above costs a printed refusal instead of a plugin. A depth check bounds it from the other side, refusing the cache root and anything deeper than `<marketplace>/<plugin>`.
  - Directories that were already empty before the run count too. They got that way by the same route, and nothing else was ever going to name them.
  - The dry run predicts them rather than discovering them mid-delete, and no-stale-versions no longer short-circuits past them. `--json` gains an `emptied` array. 13 tests (18 -> 31), covering the stray file, the symlink, the surviving sibling version, the cache root, and a `prune` call aimed outside the cache entirely.
  - SKILL.md said deletion was limited to directories exactly three levels under `cache/`. That is now false, and a governance file that describes a narrower blast radius than the tool has is worse than one that says nothing.
- **`screenscribe` is now `watchwith` (v1.0.0, marketplace 1.29.0).** The old name described the mechanism — sample the screen, scribe what it said — and the mechanism is the least interesting part. The capability is that a model which cannot see or hear gets handed a facsimile dense enough to learn from: a frame per second, each one married to the words spoken over it. `watchwith` names that. It also survives being said out loud, which the previous name did not.
  - The plugin, the skill, the script and the tests all move: `/screenscribe:screenscribe` becomes `/watchwith:watchwith`, `screenscribe.py` becomes `watchwith.py`, `$SCREENSCRIBE_BUNDLES` becomes `$WATCHWITH_BUNDLES`, and the bundle root moves from `~/.screenscribe/bundles` to `~/.watchwith/bundles`.
  - **No legacy fallback reads the old root.** A permanent `if the old path exists` branch is cruft paid for on every invocation to serve a one-time move. Bundles carry no absolute paths — verified across four bundles totalling 640 MB, zero hits for a home-directory prefix in `meta.json` or `BUNDLE.md` — so `mv` is the whole migration. The venv is the exception and cannot move: its shebangs and `pyvenv.cfg` hard-code the old prefix, so it is deleted and `bootstrap` rebuilds it, which is what `bootstrap` already existed to do.
  - Version resets to 1.0.0 rather than continuing 0.7.8. The identity is new, and eight releases and two review rounds is past the point where a leading zero is honest about the stability on offer.
  - CHANGELOG history and `docs/code-reviews/screenscribe-*.md` keep the old name. Those entries and those reviews describe releases that shipped as `screenscribe`, pinned to the SHAs they were written against; rewriting them would make the log lie about what happened. Only `docs/plans/` — live work, not a record — was renamed.
  - Fixes LOW-005 from the v0.3.0 review as a side effect: `the scribe` named BUNDLE.md, pipeline step 3 and stage 3 at once, an overload the plugin name was feeding. With the plugin named for watching, `scribe` is free to mean only the stage-3 verb, and `Watch:` citation lines now echo the plugin instead of competing with it.
- `screenscribe` (v0.7.8): **the user is not the reader.** They have usually watched the video already — the point is to teach a session that has not, and to accumulate notes worth coming back to. Stage 3 now says to write for a later session with no memory of the video rather than a recap for the person who shared it: keep the mechanism, the syntax, the numbers and the exact commands; cut "the speaker explains that…" and say what was shown. The frontmatter description picks up the same case, so a request to add an already-watched video to a growing set of notes triggers the skill.
  - A page needs a span, and stage 4 was not asking for one. It now asks a second time when a page was chosen without one, offering the screen-share segments (the default — where the payload is), a range the user names, or the whole video for short ones, with the 12 MB publish ceiling stated where the choice is made.
- `screenscribe` (v0.7.7): **the stage 3 to stage 4 boundary is always a stop.** Previously the skill only asked about what to produce when the user had not already said. But what the user said before the scribe existed was a guess: they had not seen the frames yet, and neither had the model. "Scribe this and write me notes" answers a question nobody could answer at the time it was asked. An instruction now counts as an answer only if it was given with the scribe in hand; otherwise both questions are asked in one `AskUserQuestion` call, including the one the opening message appeared to settle.
  - A third branch guards the case this would otherwise have broken: when the user asked a question rather than for an artifact, the answer is inline and nothing is asked. That rule already existed further down the section and is now the first branch instead of a sentence duplicating it.
  - Stage 3 says to report what was found, not just how many frames were read — that report is what the stage 4 question is asked against.
- `screenscribe` (v0.7.6): **the page question fires independently of the shape question.** v0.7.3 put both behind one branch — `if the user named what they want: build exactly that` — so "write me notes on this video" answered the shape and silently skipped the page entirely. They are two decisions and naming one does not answer the other: whether the artifact is a spec or a summary says nothing about whether a page should come with it. Stage 4 now collects whichever are open and asks them in a single `AskUserQuestion` call before writing anything, so the post-processing choice is offered even when the shape was named up front.
  - The page section stopped contradicting itself. It ended with "Then publish it with the Artifact tool" while the table above it said the destination was the user's call — a leftover from before the local-file option existed. The destination is now read off the answer rather than asked a second time, which also removes a round trip.
- `screenscribe` (v0.7.5): **`index` shows a CUES column, and says when a bundle has none.** `fetch_subtitles` is deliberately non-fatal — YouTube rate-limits the caption endpoint far harder than the media one, and two builds died on HTTP 429 there before it was made recoverable — so a build can finish with every frame and no transcript. Nothing downstream said so, and a bundle whose whole premise is pairing frames with the narration spoken over them is worth flagging before someone reads it and concludes the video was silent. `none` in the column, a footer line naming the cause and the fix, and `cues` in `index --json`. SKILL.md tells the model to say so before reading such a bundle rather than after.
- `plugin-janitor` (v0.1.1): `argument-hint` in the frontmatter, matching screenscribe.
- `screenscribe` (v0.7.3, marketplace 1.28.1): the skill declares what it takes and asks before it emits.
  - `argument-hint` in the frontmatter: a YouTube URL, a bare video id, a video already scribed, or nothing. `build` accepts a URL and a bare id equally — verified against yt-dlp, both resolve to the same id — so pasting the URL straight from the address bar needs no conversion, which is the common case.
  - A `## The argument` section routes it: a name already in the index starts at stage 2, a URL or id starts at stage 1, and anything else starts at stage 3 authoring from the idea. It sits below `## Script Location` because it invokes `$PY`/`$SC`, which that section binds.
  - Stage 4 now calls `AskUserQuestion` when the user has not said what they want, instead of picking an artifact shape for them — one call covering both the shape and whether a page is wanted.
  - The page section names its destination as a choice rather than assuming publication: a local HTML file in the bundle, or a published Artifact. The page embeds another author's frames, so publishing is republishing; the local file is the default when the answer is unclear.
  - Two conditionals in the new sections were written as prose and are now pseudocode: the argument that carries both a video and an instruction, and the fallback to a local file when the page destination stays unclear. The argument block also had the branches in the wrong order — the video/instruction split has to happen before the routing that consumes it.
  - `disable-model-invocation` was considered and deliberately not set. Screenscribe's citation discipline depends on a later session auto-triggering on a `Watch:` span it finds in a spec; disabling that would leave it working from the prose summary, which the same section forbids.

### Added
- **`plugin-janitor` (v0.1.0, marketplace 1.28.0): a new plugin.** `/plugin marketplace update` fetches the whole marketplace repo, then copies each plugin whose version changed into `cache/<marketplace>/<plugin>/<version>/`. It copies; it never sweeps. Measured on one machine: 72 version bumps across six plugins, every one of them still a directory on disk unless someone removed it by hand.
  - `installed_plugins.json` records one `installPath` per installed plugin, so reachability is decidable: a version directory no `installPath` resolves to is dead. Janitor removes exactly those.
  - Dry run by default; `--yes` deletes; `--json` reports and never deletes. Stdlib only, so it runs on a bare `python3` before any venv exists — the machine whose plugins are broken is the one this runs on.
  - Deletion is limited to directories exactly three levels under `cache/`, symlinked version directories are skipped rather than followed, `remove()` re-derives that shape instead of trusting its caller, and a missing or unparseable `installed_plugins.json` aborts the run — without it every version looks unreachable.
  - It also reports plugins registered as installed whose directory is gone, and does not touch them. Found one such entry on the author's machine.
  - 18 tests. One of them caught a real defect before the first run: the post-delete self-check recovered a path by re-parsing its own display string, so a *pre-existing* dangling install was reported as "janitor removed a live install" wherever the raw and resolved paths differ — `/var` vs `/private/var` on macOS was enough. Dangling entries are now carried as structured records, not re-parsed text.

### Fixed
- `screenscribe` (v0.7.2, marketplace 1.27.2): `prune`'s one-line help still read "evict frames, keeping the scribe" — the behaviour removed in v0.7.0. It is the line `--help` shows for the subcommand, so the only description of `prune` a user sees without drilling in described the wrong command.
- `screenscribe` (v0.7.1, marketplace 1.27.1): `assets/spec-template.md` told an agent to re-open a cited span with `window <video_id> 12:04-14:30`, which argparse rejects — `window` takes `start` and `end` as two arguments. The hyphenated form is correct for the `Watch:` citation and wrong as a command, and the template used it for both, so every agent following it hit "the following arguments are required: end". Carried as INFO-002 since the v0.3.0 review; verified failing, then fixed.

### Removed
- `screenscribe` (v0.7.0, marketplace 1.27.0): **`prune --frames-only` is gone.** It evicted a bundle's frames and kept its scribe, on the argument that the scribe is 0.05% of the bytes. That argument was real and beside the point: it was never asked for, and a bundle that exists as half of itself made every consumer reason about a scribe describing frames that were not there. Across two review rounds it generated five findings — a stale `BUNDLE.md` claiming a missing frame meant the screen was unchanged (MEDIUM-004), the grep path having no recovery for that state (MEDIUM-005), the `-` column over-claiming (LOW-006), a window where a crash destroyed the scribe after the frames were already deleted (R2-002), and a banner displacing the document title (R2-003). None of the machinery survives: `mark_scribe_pruned`, `pruned_note`, `PRUNED_MARK`, the `pruned` key in meta.json, `Entry.pruned`, `Entry.reclaim`, `gain()`, the zero-gain filter in `prune_targets`, the `pruned` column in `index`, and the `pruned`/`reclaimable` fields in `index --json`.
  - `prune` now has one behaviour: it removes the bundle directory. A pruned video is gone from the library and comes back by building it again.
  - `require_frames` no longer distinguishes an evicted bundle from a broken one, because only one of those can happen now.
  - 13 tests removed as dead (249 -> 236); the suite is green on both interpreters.

### Fixed
- `screenscribe` (v0.6.1, marketplace 1.26.1): **round-1 review of the library layer — one HIGH and seven MEDIUM, all remediated.** Every finding was reproduced by execution before it was fixed, and each carries a regression test that covers the reproduced failure.
  - **HIGH — `prune --yes` deleted directories that were never bundles.** `library()` accepted any directory holding a JSON object named `meta.json`, and `drop()` then `rmtree`'d it. `meta.json` is one of the most common filenames on a developer's disk. Reproduced by destroying an npm-shaped package (`index.js` included) and a photo folder through a `--root` pointed at an ordinary directory; the only tell on screen was an empty TITLE column. A bundle now also requires the `BUNDLE.md` that `build_bundle` writes on every build, plus a `meta` naming the video, and `drop()` re-derives that signature rather than trusting its caller. The old test looked like it covered this: it rejected `.DS_Store`, `_staging` and `notes.txt` — every one of them for *lacking* a `meta.json`, so the predicate had never met a directory that had one.
  - **MEDIUM — a pruned bundle's scribe kept asserting its frames existed.** Every `BUNDLE.md` says "a missing frame means the screen was unchanged, NOT that nothing was on screen. Read the nearest earlier frame." `drop(frames_only=True)` rewrote `meta.json` and never the scribe, and `BUNDLE.md` is written in exactly one other place — build time — so a pruned bundle kept that claim until it was rebuilt. Since the grep path reaches the file without passing `window`'s guard, nothing else would have corrected it. Reproduced on a copy of a real bundle: byte-identical after pruning, first `FRAME` pointer dead. `prune` now swaps that note for one naming the rebuild command. Raised by `pe-governance` as a cross-file note from a file it was not asked to review.
  - **MEDIUM — the lazy-frame-walk optimisation did not exist.** `cmd_search`'s comment claimed frames were walked only for a bundle that matched; `library()` had already walked every bundle's frames via `dir_bytes` before a single comparison ran (instrumented: 6 walks for 3 bundles). `search` never uses the byte counts. Sizes are now measured on first access, so `search` and the name resolver touch no frames at all — verified by a test that fails if `os.walk` is called during a search.
  - **MEDIUM — `search --limit` printed bundle headers with no rows under them**, which reads as "matched, nothing to show". ### Added
- `screenscribe` (v0.6.0, marketplace 1.26.0): **library maintenance — `index`, `search`, `prune`.**
  - **`index`** — every bundle in the library: id, frames on disk, size, length, last read, title, with a reclaimable-bytes total. `--json` for the machine-readable form, which carries the URL each bundle was built from.
  - **Naming a video.** Every command that takes one — `window`, `artifact`, `prune --id`, `search --id` — accepts the id, the URL in any shape, or any words from the title or channel, matched case-insensitively. The default sits under `$HOME` rather than the working directory because a bundle runs 100-240 MB: a cwd-relative default drops that into whatever repo the user is standing in and obliges every one of them to carry a `bundles/` gitignore entry, and one video informing three projects would be downloaded three times. with the env var set, `window` also accepts a bare video id, so a spec's `Watch:` line resolves from any working directory and one video informing several repos is downloaded once rather than per checkout. A direct path that is already a bundle always wins over the library. **First plugin in this marketplace with external dependencies** — `ffmpeg` on PATH plus `yt-dlp`/`imagehash`/`pillow`. 55 stdlib-`unittest` tests cover the VTT parser, frame sampling, dedupe, timestamp naming, and windowed read-back; those needing ffmpeg or Pillow skip themselves. **Validated end-to-end against a live YouTube tutorial** (a 7:24 git-rebase screencast): 29s wall clock, 138 transcript cues, 444 frames sampled -> 312 kept, 30 MB on disk, chapters extracted. Frames at 1408px were legible down to individual commit SHAs in a `git-rebase-todo` buffer and a full `git bisect` command sequence — both moments where the narration says nothing usable ("is S for a squash."), which is the thesis the plugin exists to serve.
  - **Path traversal fixed before release (found by adversarial review, reproduced end-to-end).** `fetch()` returned yt-dlp's `info["id"]` verbatim and `cmd_build` built the output directory from it with no validation. That id is network-derived, not a constrained token: for any URL falling through to yt-dlp's generic extractor it is `unquote(<last path segment>)`, so `https://host/..%2f..%2fwork.mp4` yields the literal id `../../work`. Confirmed against installed yt-dlp 2026.8.19 and reproduced with the real `cmd_build`: frames and `meta.json` were written outside `--out`, a pre-existing `BUNDLE.md` at the traversed location was overwritten, and `sample_frames`' `shutil.rmtree` **destroyed a directory named `frames`** there — the run then reported `[done]` and exit 0. YouTube ids are `[A-Za-z0-9_-]{11}` so the documented happy path never triggered it, but nothing restricted input to youtube.com. Now: the id is sanitized to one path segment, the destination is asserted to resolve inside the output root, and `sample_frames` refuses to clear any directory containing non-`.jpg` entries. Underscore is deliberately NOT stripped during sanitization — it is legal in a YouTube id, and stripping it renamed the bundle away from the id a spec's `Watch:` line cites.
  - Found by the live run: yt-dlp's `quiet: True` does not suppress its progress bar, which writes straight to stdout and garbled the script's own output — `noprogress: True` added. The README's disk estimate was recalibrated from synthetic frames to the real run: retention depends heavily on production style, and a webcam-behind-translucent-terminal layout defeats perceptual dedupe almost entirely (70% kept, ~240 MB/hour) where a static screencast dedupes far harder.
  - Fixed before release, all three found by executing the code rather than reading it: `next(staging.glob("video.*"))` also matched `video.en.vtt` and handed the **subtitle file** to ffmpeg — on APFS `scandir` returned it first, so stage 1 would have failed on every video that has captions. The VTT rolling-duplicate strip only caught exact repeats, but YouTube's auto-captions *extend* the previous cue rather than repeating it, so a real transcript came out ~2.4x duplicated; cues are now merged against a running word tail (word-based, so a tail ending in "back" does not eat the "back" of "backend"). And `imagehash.phash()` at its default `hash_size=8` — a 32x32 grayscale DCT — cannot see screencast text at all: across six distinct terminal scenes the distinct-scene hamming distances were 0, 0, 4, 6, 14 while identical frames scored 0, so **no threshold separates them** and the shipped default of 6 discarded three of five real transitions while reporting success. `hash_size=16` scores 26 minimum between distinct scenes and 0 within identical ones.
  - Design changes from the drafted version: fixed-rate sampling replaced ffmpeg's `select='gt(scene,N)'` plus `pts_time` stderr parsing, whose file/timestamp zip was load-bearing and silently misaligned the whole bundle on any ffmpeg version difference — frame N is now at `(N-1)/fps` arithmetically, which also recovers the `t=0` opening frame scene detection never emitted. `FRAME_WIDTH` 1280 → 1408: Claude downscales anything over ~1.15 MP, so 1408x792 is the widest frame whose pixels survive, and 1280 was giving away 21% of them. JPEG q3 kept over PNG after measuring SSIM 0.995 / PSNR 42.7 dB on h264-sourced terminal text — token cost is set by pixel dimensions, so PNG's 2.8x disk buys only a faithful copy of h264's own artifacts. The build-time cull to 60 frames was removed entirely; `window` enforces the budget instead.
  - `--gemini` was **cut before release** rather than ported. It emitted `extraction.md` — Gemini's already-compressed reading of the video — which is derived evidence that fails for the same reason a transcript does: a spec citing it cites a claim, where a spec citing a frame cites a source. It also carried the plugin's only API key, its only second vendor, and a code path that had never executed. Verified against Google's live docs in the process: the Interactions API went GA in June 2026 and `generate_content` is legacy-but-supported (so the call was stale, not broken), and the plan doc's claim that text goes *after* the video part contradicts the current YouTube example, which puts text first. `docs/plans/screenscribe-gemini-ingestion.md` records the decision and the follow-up worth building — let Gemini pick *which timestamps matter*, then cut frames there with ffmpeg and read the pixels ourselves.
  - The skill's internal `PLAN.md` was deleted rather than shipped — it was a working status file distributed to every installer. Its surviving open questions moved to `docs/plans/screenscribe-gemini-ingestion.md`. References to a `/goal` command were removed from both READMEs: no such command exists in this marketplace.
- `code-reviewer` (v2.9.0, marketplace 1.19.0): **Spec Coverage pass** for story-linked PRs. New `skills/code-reviewer/assets/spec-coverage-protocol.md` asset holds the authoritative protocol — acceptance-criteria parsing, PR-description checklist parsing, evidence verification (commit SHA / file:line / keyword grep), deferral verification, and YAML output shape. SKILL.md's new Phase 4.5 is calling-agent-only: it detects story-link via `gh issue view <N> --json labels`, resolves the story file (caller-provided `STORY_FILE`, local `docs/epics/*/.github-state.json` mapping, or GH issue body fallback), and **enriches each dispatched PE's input with `STORY_LINKED: true`, `STORY_FILE: <path>`, `SPEC_COVERAGE_PROTOCOL: <absolute path>`, `PR_NUMBER: <N>`.** All 5 PE agents (`pe-go`, `pe-vue`, `pe-aws-infra`, `pe-governance`, `pe-devtools`) gain a slim "Spec Coverage" section that triggers on `STORY_LINKED: true` by Reading the asset and following its protocol — producing `SPEC-MISSING-*`, `SPEC-EVIDENCE-MISSING-*`, `SPEC-DEFER-INVALID-*`, `SPEC-DEFER-CLOSED-*`, `SPEC-WEAK-EVIDENCE-*`, and `SPEC-FORMAT-*` findings alongside their stack findings. PEs may optionally annotate stack findings with `discharges_ac: ["AC-N"]` metadata. The asset-based design keeps the protocol authoritative in ONE file while ensuring the reviewer agents (who do NOT see SKILL.md) actually have access to it — addressing the architectural concern that placing reviewer-facing rules in SKILL.md leaves them invisible to the agents that need them. Multi-PE dispatch produces duplicate SPEC findings; Phase 4 de-duplication consolidates them. Non-story PRs (chores, bugfixes, tasks) keep the four-pass protocol unchanged. Motivated by the Corebizy Phase 5/6 incident where Story #1435 PRs shipped without integrating the Story #1443 hardening payload they were contracted to ship — narrow code change passed all four reviewer passes, story acceptance criteria were not verified, gap discovered downstream.

### Fixed
- `issue-manager` (1.0.5) and `session-analyzer` (1.0.3): the script resolver's fail-loud path did not survive `set -e`. `VAR=$(python3 -c "…")` where the python exits 1 kills the shell **at the assignment**, so the guard never ran and the `find ~/.claude/skills` manual-install fallback was dead code — an agent that prepends `set -euo pipefail` (routine) got a bare exit 1 with no message. Both command substitutions now end in `|| true`. The `find` one needs it too: `find` exits 1 when `~/.claude/skills` is absent, and that assignment is the final command of its `&&` list, so the `set -e` exemption for AND-lists does not cover it.
- `issue-manager` (1.0.5) and `session-analyzer` (1.0.3): matching on plugin name alone made resolution first-match-wins in JSON insertion order. With both the old and new marketplace identifiers present — the exact post-rename state — a stale entry pointing at an older cached version could win permanently and silently, and an unrelated marketplace shipping a same-named plugin could shadow this one. Entries from this marketplace now sort first, with any other marketplace as fallback.
- `issue-manager` (1.0.5) and `session-analyzer` (1.0.3): `entry.get('installPath', '')` turned a missing `installPath` into a **CWD-relative** path, so `.is_file()` was evaluated against whatever directory the skill happened to run in and could resolve — and then execute — an unrelated file with exit 0. Entries without `installPath` are skipped, and the resolved path must be absolute.
- `issue-manager` (1.0.5) and `session-analyzer` (1.0.3): a structurally malformed registry (`plugins` as a list, entries as a string) raised an uncaught `AttributeError` and dumped a traceback ahead of the real message, now that `2>/dev/null` is gone. The guard catches any exception and rejects a non-dict `plugins`.
- Dropped the "canonical — always points to the active version" claim from both SKILL.md files. The resolver never guaranteed that, and after the changes above it explicitly does not.
- `code-reviewer` (v2.7.3, marketplace 1.17.3): all 5 PE agent definitions (`pe-go`, `pe-vue`, `pe-aws-infra`, `pe-governance`, `pe-devtools`) now grant the full lifecycle toolkit. Previously each PE was granted only 8 tools (`Read, Write, Bash, Grep, Glob, SendMessage, WebSearch, WebFetch`) — designed as one-shot YAML returners with no lifecycle awareness. With team-mode dispatch, multi-round review protocols, and round-to-round continuity contracts, that 8-tool baseline is structurally insufficient. New baseline: `Read, Write, Edit, Bash, Grep, Glob, WebSearch, WebFetch, SendMessage, ScheduleWakeup, TaskCreate, TaskUpdate, TaskList, TaskGet, ToolSearch, Skill` (16 tools). Added: `Edit` (efficient diff-mode edits to review docs), `ScheduleWakeup` (lightweight one-shot polling for multi-round dispatch), `Task*` (receipt-per-tick contract enforcement), `ToolSearch` (deferred-tool introspection), `Skill` (composable skill invocation, e.g., for slack-messaging during review). Deliberately NOT added: `Cron*` (heavy, ScheduleWakeup sufficient), `Monitor` (silent-failure mode), `Team*` (reviewers should not create teams), `AskUserQuestion` (reviewers report findings via SendMessage, not interactive user prompts). Brings plugin PEs to feature parity with project-level engineering agents.
- `code-reviewer` (v2.7.2, marketplace 1.17.2): all 5 PE agent definitions (`pe-go`, `pe-vue`, `pe-aws-infra`, `pe-governance`, `pe-devtools`) now bake the team-mode delivery contract into their own Workflow step. Previously the contract lived only in the calling-agent dispatch input (SKILL.md), so PEs invoked from custom calling-agents that omitted the delivery clause would render YAML in session and idle without SendMessage. Now PE definitions self-contain the contract: `match invocation_mode: foreground → return YAML as tool-result; background-teammate → SendMessage(to: "team-lead", message: <yaml>)`. PEs deliver correctly regardless of dispatch site.
- `code-reviewer` (v2.7.1, marketplace 1.17.1): SKILL.md `§ Dispatch Input` now specifies an explicit DELIVERY CONTRACT split by invocation mode. Previously, "Return YAML findings" was ambiguous — when calling agents dispatched PEs with `team_name` set (background teammate mode), PEs would render YAML in their session and idle without calling the SendMessage tool, leaving the calling agent with no findings. Now: foreground dispatch returns YAML as tool-result; background-team dispatch delivers YAML via SendMessage to the team lead. Calling-agent contract clarified to treat team-mode dispatches as async with SendMessage delivery, not synchronous tool result.
